# macOS 0.9.11 内存排查

[English](memory-investigation.md)

2026 年 11 月 10 日，已安装的 0.9.10 进程连续运行约六天。physical footprint 达到 **3.6 GiB**，首次 `ps` RSS 却只有 **126 MiB**。`heap` 统计到 **27,396,411 次存活分配、3,287,755,456 字节**，包括 53,301 个表格行、53,361 个单元格、106,666 个布局引擎及数十万约束。文档只有五个，编辑面板只有一个；绘图区域、文本和撤销对象无法解释主要分配量。

可以直接处理的原因是旧界面对象被持续持有。旧侧栏单元格的引用链经过 `NSToolTipManager._toolTipsByView` 的强引用和通知回调，再持有整行及布局图。此前每次请求侧栏单元格都新建控件并设置路径提示，没有复用标识，也没有在移除时显式注销提示。文件事件重建项目树、恢复展开目录并定位活动文件，反复触发这条路径。`leaks` 仅报告十个不可达分配、共 560 字节；它不会把仍可达但不应继续持有的对象算作泄漏。自动释放池约 10.4 MiB，同样不足以解释总量。

0.9.11 只在单元格创建时构建标签、图标和约束，设置固定复用标识，通过 AppKit 的 `makeView(withIdentifier:owner:)` 复用。侧栏行退出显示或单元格直接脱离父视图时注销路径提示，复用时更新名称、图标、颜色和路径。行视图本身也通过固定标识复用。命令面板、项目搜索结果也采用相同方式。文本、编码、撤销和恢复继续由原有模块管理。

移除提示的附加测试刻意保留已移除单元格的强引用，确认其提示清理不会因对象已销毁而虚假通过。

原生负载创建 80 个文件，反复重建/恢复侧栏并移动视口，将鼠标留在侧栏，刷新之间不注入合成输入。记录 physical footprint 和行/单元格弱引用，同时验证旧单元格清除提示、当前路径与名称一致、子控件数量没有增加。最终完成 **1000 次刷新**，每个检查点均只有 **26 个被跟踪的行和 26 个单元格**存活。末八个检查点从 **72.32 增至 73.30 MiB**，采样 RSS 峰值 **106.70 MiB**。这证明已跟踪界面生命周期有界，但仍有分配器/框架增长，不代表总内存绝对恒定。

旧版本的较短负载同样只保留 26 个被跟踪的行/单元格，**没有复现六天累积的完整过程**。真实堆与引用链定位了持有问题；短测试验证行为和生命周期。本报告不声称严格 A/B 提速或长期内存降低比例。

已验收的 Universal 0.9.11 在正常退出后安装，保留旧应用及支持目录快照。安装程序摘要、运行 bundle 路径与验收产物一致，只有一个正式应用实例。启动后 footprint **102.4 MiB**（峰值 141.6 MiB），堆分配约 **42.9 MiB**，侧栏单元格/行各 78 个。新进程有两个文档，旧进程有五个，因此重启后的数值是当前观测，不能当作严格优化 A/B。随后约每 45 秒采样得到 112.2、112.3 MiB；行/单元格从 78 个暖启动到 115 个，随后保持 115 个。短期观测不能证明多天稳定。

验收通过 20 项核心检查、66 项日常功能检查、33 项主页 UI 和 37 项日常 UI，包含实际 FSEvents、项目搜索，以及文档/可移植性验证。Universal ARM64/Intel 均编译成功；未验证实体 Intel 和 Windows 运行。多展开目录、提示交互、切换项目、持续外部文件活动仍需长期观察。文件事件仍会重新索引工作区；细粒度增量刷新属于后续性能任务。

证据位于忽略的 `.build/test-results/memory-20261110/`（旧进程 vmmap、堆、泄漏/自动释放池/引用链、编译、UI 检查、产物摘要和安装），以及 `.build/performance/memory-final-tooltip/`（固定测试应用、输出和指标）。在应用目录复现：

```sh
python3 tests/run_performance.py sidebar-memory --cycles 20 --cases sidebar:65536 --timeout 120
```

安装及验收规则见[开发指南](development.zh-CN.md)。RSS 不包含已经压缩或回收的驻留页，不能与 footprint 混用。
